# 08 · Caveat registry

The single home for every `CaveatId` the `Caveat` component (`03-components.md` §5) can take. `lib/copy/caveats.ts` is generated from table 1; `lib/copy/caveats.test.ts` pins each phrase; a screen spec's §5 table names an id here and says where it sits, nothing more.

What a caveat is, per 03 §5: *the limit that travels with a result*, pinned by exact phrase, placed on the same row as the number or label it limits. A string that explains a control, a storage rule or a flow is not a caveat; those are hint strings and live in table 2 so no phrase the screens already carry is lost.

Rules this registry applies:

- The classifier runs the keyword scan **or** the judge, never both (`classifier.py:53-60`). Every phrase that said "scan plus judge" is rewritten; the spec-edit table (table 3) lists where.
- Which judge exists is decided once, at startup (`app.py:101-108` calls `get_best_available_backend()` in the lifespan): Anthropic, then OpenAI, then Google, then an Ollama at `localhost:11434` with at least one model (`llm.py:143-184`). An xAI or Together key never gives a judge. Saving an Anthropic key in dev mode rebuilds the runner without a backend (`app.py:2303-2306`), so the judge is gone until restart.
- Duplicates are merged under one id; false phrases are corrected to the code; three SWE-bench ids are kept as **reserved** because SWE-bench is deferred (Architect steelman) and the ids are already in `benchmarks.md` §11.
- Counts: the screen specs plus `benchmarks.md` §11 and `03-components.md` §5 carried **144 distinct ids** (230 table rows). This registry has **60 caveat ids** (3 reserved), **46 hint strings**, and 7 ids retired outright.

Screen abbreviations: as in `07-glossary.md` (wb, home, sess, lib-p, lib-c, lib-pol, lib-s, lib-v, dlg-s, dlg-p, st-list, st-new, repeat, framing, models, context, over-time, exp-list, exp-new, exp, res, score, pub, set, splash, ov, b-cat, b-suite, b-new, b-run).
